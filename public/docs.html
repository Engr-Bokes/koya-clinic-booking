01 / ORIENTATION

One origin. Separate interfaces.

The frontend and backend share a host, but the API has its own /api prefix. The patient interface is not an API response.

  • /
    Patient demo

    Browser interface for finding, booking and cancelling fictional appointments.

  • /api
    Public API discovery

    GET /api returns service metadata without a key. It is not a clinical endpoint.

  • /docs
    This guide

    Public, static documentation. No credentials or live request runner.

  • /docs/openapi.json
    Machine-readable contract

    Public OpenAPI document. Use the base URL above with its relative endpoint paths.

The backend runs as a serverless Node.js/Express service with durable PostgreSQL storage. Legacy root endpoints such as /slots and /bookings remain for backwards compatibility; use /api/slots and /api/bookings for new integrations.

02 / ACCESS

Bring your assessment key.

The assessment owner shares the API key privately with authorized reviewers. There is no signup flow or public key generator. If you do not have a key, request it from the owner rather than looking for one in this page or the source code.

Required on every clinical endpoint

X-API-Key: YOUR_API_KEY
  • Send the key in the X-API-Key header, never in a URL or query string. Missing or incorrect keys return 401.
  • For JSON request bodies, also send Content-Type: application/json. The request body limit is 1 MB.
  • Only the public pages, contract and discovery metadata are key-free. All slot, booking and reset operations require a key.
  • The patient demo accepts the key manually. It stays in memory unless you opt in to session storage for that tab; it is not saved in local storage.

Never commit a key, paste it into a public issue, include it in screenshots, or embed it in frontend code. These examples contain only the placeholder YOUR_API_KEY.

03 / FIRST REQUESTS

List, book, then manage.

Run these commands in a local shell with curl. Replace the key placeholder privately. The commands below do not reset the dataset. Booking and cancellation do change the shared assessment data.

  1. Set your base URL and key

    BASE_URL='https://careslot-chibuokem.vercel.app/api'
API_KEY='YOUR_API_KEY'

    These are shell variables, not query parameters. Keep your shell history private.

  2. Find an available future slot

    curl --silent --show-error --include \
  --header "X-API-Key: $API_KEY" \
  "$BASE_URL/slots"

    Read slots in the response. Pick an item with available: true and a future start. Availability alone does not mean a slot is in the future. Copy its returned id for the next step.

    Filter by an exact provider name
    curl --silent --show-error --get \
  --header "X-API-Key: $API_KEY" \
  --data-urlencode 'provider=Dr Ade' \
  "$BASE_URL/slots"

    Use a provider from the actual response. The filter is case-sensitive and is not a partial search.

  3. Create one fictional booking

    Replace SLOT_ID with the exact slot ID you just received. Keep the same body and idempotency key if you need to retry this particular request.

    curl --silent --show-error --include \
  --request POST \
  --header "X-API-Key: $API_KEY" \
  --header 'Content-Type: application/json' \
  --header 'Idempotency-Key: booking-example-001' \
  --data '{"slot_id":"SLOT_ID","name":"Alex Example","email":"alex@example.com"}' \
  "$BASE_URL/bookings"

    Success is 201 with a booking object. Save its id as your booking reference. Repeating the identical request with that key replays the same response, not a second booking. Use a new unique idempotency key for a genuinely new booking attempt.

  4. Look up or cancel your booking

    Replace BOOKING_ID with the returned booking id, not its slot_id.

    Lookup is read-only

    curl --silent --show-error --include \
  --header "X-API-Key: $API_KEY" \
  "$BASE_URL/bookings/BOOKING_ID"

    Cancellation changes the booking and frees its slot

    curl --silent --show-error --include \
  --request DELETE \
  --header "X-API-Key: $API_KEY" \
  "$BASE_URL/bookings/BOOKING_ID"

    Cancellation returns the object with status: "cancelled". Repeating a cancellation returns 409, not another success.

  5. Page through bookings for an email

    First page

    curl --silent --show-error --get \
  --header "X-API-Key: $API_KEY" \
  --data-urlencode 'email=alex@example.com' \
  --data-urlencode 'limit=10' \
  "$BASE_URL/bookings"

    If next_cursor is a string, replace NEXT_CURSOR below with that exact value. Keep the same email. Stop when next_cursor is null.

    Next page, only when a cursor was returned

    curl --silent --show-error --get \
  --header "X-API-Key: $API_KEY" \
  --data-urlencode 'email=alex@example.com' \
  --data-urlencode 'limit=10' \
  --data-urlencode 'cursor=NEXT_CURSOR' \
  "$BASE_URL/bookings"

04 / REFERENCE

The clinical endpoints.

Every endpoint below requires X-API-Key. Paths include the preferred /api prefix. Responses are JSON; errors use {"error":"message"}.

GET

/api/slots

List all slots, including occupied and past slots, with a boolean available. A slot is unavailable while it has a confirmed booking.

  • Optional provider: exact, case-sensitive match. No trimming or partial matching is applied by the API. Omit the parameter for all providers.
  • Sorted by start ascending, then id for ties.
  • 200: {"slots":[...]}. Each slot has id, provider, start, end, available. No matches yields an empty array.
  • 400: invalid provider parameter, such as repeated query values.
POST

/api/bookings

Create a confirmed booking for one future slot. Optional header: Idempotency-Key. See retry semantics before retrying.

Required JSON body

{
  "slot_id": "SLOT_ID",
  "name": "Alex Example",
  "email": "alex@example.com"
}
  • All three fields must be nonempty strings. Email must have a valid basic email format. slot_id must match an existing slot exactly.
  • Name and email have surrounding whitespace trimmed; stored email is lower case. Internal name spacing is preserved.
  • A slot whose start is at or before the server's current time cannot be booked.
  • 201: booking object with id, slot_id, name, email, status: "confirmed" and created_at.
  • 400: missing/invalid fields, already-started slot, invalid JSON or blank idempotency key. 404: slot not found. 409: slot already booked. 422: idempotency key reused with a different body. 429: email attempt limit reached.

Concurrent requests cannot create two confirmed bookings for the same slot. PostgreSQL transactions, row locks and a partial unique index enforce that invariant.

GET

/api/bookings/{id}

Retrieve a booking by its returned booking ID, including a cancelled booking.

  • 200: booking object.
  • 404: booking does not exist.
DELETE

/api/bookings/{id}

Change a confirmed booking to cancelled and release its slot. The booking record is retained.

  • 200: cancelled booking object.
  • 404: booking not found. 409: booking already cancelled.
GET

/api/bookings?email=…

List both confirmed and cancelled bookings for one email, oldest first. Ordering uses created_at, then id for stable pagination.

email required
A valid email. Matching ignores case and trims surrounding whitespace.
limit optional
Integer from 1 to 50; default 10. Values such as 0, 51, 1.5 or 01 are invalid.
cursor optional
Use the previous response's opaque next_cursor unchanged. It is tied to the email; do not construct it or reuse it for another email.
  • 200: {"bookings":[...],"next_cursor":null}, with a cursor string instead of null when more results exist.
  • 400: missing/invalid email, invalid limit or invalid/mismatched cursor.
POST

/api/reset

DESTRUCTIVE
Evaluator and isolated tests only. Reset deletes ALL bookings, replaces ALL slots, and clears ALL idempotency records and rate-limit attempt history. It affects every user of the shared dataset. Do not run it to try the patient demo.

Requires the same X-API-Key header. Supply {"slots":[...]}. Each slot requires nonempty string id and provider, and valid ISO date-time strings start and end with a timezone. IDs must be unique and end must be after start.

  • Past slots are allowed in reset, but cannot subsequently be booked.
  • An empty slots array clears the dataset. Validation completes before any data is replaced.
  • 200: {"ok":true}. 400: missing slots array, invalid slot, duplicate ID or invalid time range.

Replacement and bookkeeping cleanup happen atomically under an exclusive database lock. This endpoint is intentionally not part of the quickstart.

05 / RELIABLE REQUESTS

Retry a request, not a booking.

Idempotency on booking creation

Choose a unique Idempotency-Key for each new POST /api/bookings operation. It is separate from your authentication key.

  • Same key, same body: the stored status, response body and headers are replayed. A successful retry returns the same 201 and booking ID. Stored failures are replayed too.
  • Same key, different body: 422, even if you only change name/email whitespace or email case. Request identity is checked before those values are normalized. JSON object property order does not affect identity.
  • Precedence: key replay or different-body rejection happens before email rate limiting. Neither consumes another attempt. Authentication and JSON parsing still apply.
  • Cached throttle: retrying a key with a stored 429 replays that failure, including its original Retry-After. Wait, then use a new key for a genuinely new attempt.

Idempotency keys share the assessment dataset's namespace. Do not reuse a sample key for unrelated operations. Stored responses persist until reset; replaying a successful creation after cancellation returns the original creation response, not the booking's current state. Use lookup to check current status.

Five attempts per email, per rolling minute

New booking attempts with a nonempty normalized string email are tracked in a rolling 60-second window. The first five proceed to booking validation; the sixth is rejected with 429. Other emails have independent buckets.

  • Failed attempts count, including validation errors, missing slots, conflicts and 429 responses. Repeated throttled attempts can extend the wait.
  • Retry-After is a positive integer number of seconds, not a date. Wait at least that long before making a new attempt.
  • A missing, blank or non-string email has no email bucket and fails validation. An invalid but nonempty string email can still consume an attempt.
  • Only new booking creation attempts use this limiter, not listing, lookup or cancellation. Idempotent replays do not consume the limit.

Example throttle response

HTTP/1.1 429 Too Many Requests
Content-Type: application/json
Retry-After: 60

{"error":"Too many booking attempts"}

06 / RESPONSES

Read the status, then the message.

Clinical API errors use a JSON object such as {"error":"Slot not found"}. Do not assume every failure is safe to retry immediately.

  • 200
    OK

    Read, cancel or reset completed.

  • 201
    Created

    Booking confirmed, or the original successful response replayed.

  • 400
    Bad request

    Check body, email, dates, query parameters or cursor. Already-started slots also return 400.

  • 401
    Unauthorized

    Send the correct X-API-Key header. Putting a key in the URL does not authenticate.

  • 404
    Not found

    The requested slot, booking or API route does not exist.

  • 409
    Conflict

    Slot already booked, or booking already cancelled.

  • 413
    Payload too large

    Keep JSON request bodies within the 1 MB parser limit.

  • 422
    Idempotency mismatch

    The same idempotency key was used with different request data.

  • 429
    Too many attempts

    Respect Retry-After. A cached 429 needs a new key for a new attempt after waiting.

  • 500 / 503
    Service error

    Unexpected backend failure or temporary service unavailability. For an uncertain booking result, retry the same body with its original idempotency key.

07 / ASSESSMENT BOUNDARIES

Built for a clear evaluation.

  • Not patient authentication. Anyone holding the shared assessment key can use clinical endpoints, look up bookings and invoke reset. Knowing an email or booking ID is not proof of patient identity.
  • Use fictional details only. Do not submit real patient names, emails, medical information or other sensitive data. This demo is not a production clinical system.
  • Durable, shared state. PostgreSQL stores slots, bookings, idempotency responses and attempts across serverless invocations. Browser refreshes do not reset them. Reset does.
  • Server time is authoritative. API date-times include a timezone. Compare instants rather than formatted text. The patient UI displays appointment times in Africa/Lagos, WAT (UTC+1).
  • Keep the submitted deployment unchanged. After assessment submission, do not change the deployment, rotate its evaluator key, reseed/reset shared data or take the service offline unless instructed by the evaluator.

This page explains the implementation and contract. It is not a claim of production readiness or a live deployment verification report.
